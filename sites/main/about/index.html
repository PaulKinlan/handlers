About this site

This site started with the step that comes before two web apps can talk to each other: how does one of them get opened in the first place? It turned into a set of working demos of the ways a web app can connect to the operating system and to other apps.

How it started

Port Authority is my set of experiments with MessagePort: what two sites can do once each holds one end of a channel. It begins with two pages that already have a port to each other. It does not cover how an app gets opened to begin with, by a link with a scheme of its own, a file double-clicked in the operating system, or a share from another app. The browser and the operating system own those routes, and an app can only register for them. This site is about those registrations.

I have written about this for a long time. Web Intents was an attempt at one way for an app to ask for an action, for another app to provide it, and for an answer to come back. It was withdrawn. What the platform has instead is a separate API for each kind of action: protocol handlers, file handlers, share targets, payment handlers. This site puts them in one place, running, to show what each one can and cannot do.

The first version, in November 2026, was three sites: a hub, a notes app and a tasks app, each on its own origin, so that a link or a file on one origin could open an app on another. It was called Handlers.

From handlers to the rest of the site

Every one of these registrations belongs to an origin, so every demo app here has an origin of its own. A link on the hub opens Notes, which is somewhere else. A share from Tasks arrives in Notes. Nothing is faked on one page.

The next pieces were the census, which checks each way a web app can be opened in the browser you are reading with, the list of what is missing, and Reader and Charts, where an app that was handed a file by the operating system lends it to an app on another origin. That demo is where this site and Port Authority meet: the file arrives through the operating system, and it is lent across origins over a port.

After that the list went past handlers. What can an installed app do with its title bar, with tabs, or with a window that stays on top? Can a page install an app on another origin? Can an installed app move to a new address? Which routes give the caller an answer, such as a payment or a credential, and which do not? The site was called Handlers until it got its domain.

Each pattern has a page of its own with the same parts: a diagram of who sends what to whom, a demo that uses the apps here, the checks for the browser you are reading with, how it works, what you could build with it, and what goes wrong.

What it is for

A native app can be opened by a link scheme, a file type or a share, and can hand a result back to whatever opened it. The web has most of the first half of that now. It has very little of the second: a handler is given a string, a form or some file handles, and the app that started it hears nothing back.

So the site does three things. It shows what works today, with demos you can run. It writes down what goes wrong, on every page. And it says what is missing: What web app integration is missing is the list of what I want browser vendors to build or fix, with a check for each gap where one can be run.

It is also meant to be used on other sites. The agent skill is one file that you give to a coding agent. The agent reads your codebase, your manifest and your plans, checks them against the patterns here, and reports which integrations fit your site and which ones to skip.

Who built it and how it works

I'm Paul Kinlan and I lead the Chrome and Open Web Developer Relations team at Google. This is my own set of experiments, not official Chrome documentation.

There is no framework and no bundler. The pages are plain HTML and ES modules. One Cloudflare Worker script picks a folder of files by hostname, which is how the hub and every demo app live in one repository and still have an origin each.

Not every demo has been run on every platform. The checks on each page run in your browser when you open it, but the demos that need ChromeOS, a wallet that holds a credential, or signing out of the computer have not been run from end to end. If one does not work for you, or something here is wrong, please open an issue.

Browser support

Most of what is here works in Chromium only, and a lot of it on desktop only. A few parts work more widely: sharing, badges, and registerProtocolHandler in a tab. Each pattern page says where it works under "What goes wrong", and the census checks the browser you are reading with.
